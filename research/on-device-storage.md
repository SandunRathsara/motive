# On-device storage for the Personal Health Record

Research date: **1 November 2026**. Resolves [research ticket #5](https://github.com/SandunRathsara/motive/issues/5), under [roadmap #1](https://github.com/SandunRathsara/motive/issues/1). **Research, not an accepted storage decision or implementation.**

## Scope and evidence limits

The question is a single-user iPhone Expo application, New Architecture, with health, nutrition, workouts, plans and chat stored locally; offline workout logging and offline Food Draft capture, upgrades without data loss, portable export and hard delete are mandatory. The branch still has no root `package.json` or lockfile. Its authoritative documents leave persistence explicitly undecided: [stack §5](../docs/TECH_STACK.md#5-persistence-decision-gate), [architecture §§4–6](../docs/ARCHITECTURE.md#4-import-boundaries), [product §§10–12](../docs/REQUIREMENT.md#10-data-model--source-of-truth-rules). The ticket's production scope is not the product document's in-memory HTML prototype.

**Version caveat:** the live Expo `latest` SQLite page retrieved for this research identifies **SDK 58** in its navigation/source branch; the Context7 index offered SDK branches through 56. Use the live SDK-specific reference and installed lockfile at bootstrap, not the index as a release calendar. No app was bootstrapped and no native build, benchmark, backup/restore or migration was executed. Exact release/package combinations remain **unverified**. Expo documents all SDK `expo-*` modules as New-Architecture compatible since SDK 53 and New Architecture as mandatory from SDK 55. [Expo SQLite](https://docs.expo.dev/versions/latest/sdk/sqlite/), [Expo New Architecture](https://docs.expo.dev/guides/new-architecture/).

## Short answer

**Leading candidate for the decision: `expo-sqlite`, with explicit versioned migrations; evaluate SQLCipher separately from whether to add Drizzle.** SQLite provides relational queries, transactions and export primitives; Expo supplies SDK integration and an optional SQLCipher build. Drizzle adds typed schema/query tooling and generated, bundled migrations, not a different persistence or security engine. This is a simplicity judgment based on the documented capabilities, not a performance comparison. [Expo SQLite](https://docs.expo.dev/versions/latest/sdk/sqlite/), [Drizzle Expo integration](https://orm.drizzle.team/docs/connect-expo-sqlite).

The two high-consequence decisions are **backup policy** and **key recovery**, not speed: Documents/Application Support normally enter device backups; a device-bound SQLCipher key cannot make an encrypted database restored onto another device readable. A strict on-device-only promise therefore needs an explicit backup-exclusion policy and an honest device-loss warning. [Apple file placement and backup rules](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html), [SecureStore accessibility constants](https://docs.expo.dev/versions/latest/sdk/securestore/#constants).

## Transactions, migrations and durability

### What “survives upgrades” must mean

Expo documents persistence across restarts, not automatic schema evolution. Its iOS implementation places the default DB under Documents/SQLite. Apple distinguishes the replaceable app bundle from the persistent data container; durable records must not live in bundle assets, cache or temporary directories. Upgrade preservation therefore requires both correct placement and tested app migrations, not merely choosing a library. [Expo persistence](https://docs.expo.dev/versions/latest/sdk/sqlite/), [iOS source](https://github.com/expo/expo/blob/sdk-58/packages/expo-sqlite/ios/SQLiteModule.swift), [Apple directory rules](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html).

**Proposed migration contract:** open/protect/key the database; read schema version; refuse unsupported newer versions without deleting anything; run each required migration and its version update atomically before consumers mount. Keep the full supported upgrade chain and test skipping several releases. On corruption, wrong key, migration failure or insufficient disk space, preserve files and surface recovery/export choices—never silently seed/reset. Expo's startup/migration guidance and WatermelonDB's reset warnings explain why this is necessary. [Expo migration guidance](https://github.com/expo/expo/blob/main/packages/expo-sqlite/skills/expo-sqlite/SKILL.md), [Watermelon edge cases](https://watermelondb.dev/docs/Advanced/Migrations#database-reseting-and-other-edge-cases).

Expo's `withTransactionAsync()` can include unrelated queries that run while the transaction is open. `withExclusiveTransactionAsync()` scopes queries through a transaction-specific connection, but that connection **does not inherit a SQLCipher key set with SQL on the original connection**. Proposal: centralize database access; serialize a keyed single-connection transaction path, or prove explicit initialization of every transaction connection on the installed version. Do not combine the two APIs and assume encryption just works. [Transaction docs](https://docs.expo.dev/versions/latest/sdk/sqlite/#executing-queries-within-an-async-transaction), [Expo SQLCipher connection warning](https://github.com/expo/expo/blob/main/packages/expo-sqlite/skills/expo-sqlite/references/web-and-config.md#sqlcipher).

**Proposed write units:** set + session progress, Food Draft + capture metadata, finalized food + draft disposition, accepted proposal + new PlanVersion should each commit together. Show immediate optimistic feedback if desired, but only label data saved after local commit; recover active workout/drafts from DB after process death. Make capture idempotent with unique IDs. These are design proposals enabled by [Expo transactions](https://docs.expo.dev/versions/latest/sdk/sqlite/#executing-queries-within-an-async-transaction) and [op-sqlite transactional batches](https://op-engineering.github.io/op-sqlite/docs/api#batch-execution).

If photos are external files, DB transactions cannot atomically commit the filesystem too. Proposed capture protocol: move photo into a protected, nonpurgeable app-owned location, then commit draft reference/status; reconcile orphan files or incomplete captures after interruption. The attachment's protection/backup/deletion policy must match the record. SQLite's transaction scope is the database, while Apple independently defines filesystem storage classes/locations. [SQLite transactions](https://www.sqlite.org/lang_transaction.html), [Apple files](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html).

## Queries and state ownership

**Proposed local schema scope:** profile/settings, targets/versions, exercises, sessions, sets, Food Drafts, food entries, recipes/saved meals, health samples with provenance, per-signal availability/sync cursors, insights/evidence references, plan proposals/versions and coach threads/messages/citations. This extends the branch's [entity inventory](../docs/REQUIREMENT.md#10-data-model--source-of-truth-rules) with ticket-required durable capture drafts; no final schema is selected here.

For 14-day trends, propose indexed sample type + timestamp, food day key, session date, and set session/exercise references; range-filter and aggregate in SQL rather than loading lifetime history. SQLite supports windowed `AVG`; importantly, **seven rows is not seven days** when days are missing or have multiple readings. First apply provenance/day precedence, use calendar-day ordinals/range frames (or a small pure calculation over the bounded result), preserve missingness and read six additional preceding days for a complete first 7-day point in a 14-day chart. These are algorithm proposals grounded in SQLite's distinction between ROWS/RANGE and the product's day/source rules. [Window frames](https://www.sqlite.org/windowfunctions.html#frame_specifications), [product rules](../docs/REQUIREMENT.md#10-data-model--source-of-truth-rules).

**Architecture fit proposal:** one cross-feature database lifecycle facility under `/lib`, feature-owned repository/service adapters under `/features/<domain>/services`, and Zod validation at stored-record/import/native boundaries. SQLite, not a cache or persisted Zustand snapshot, owns durable PHR facts. Zustand can expose active-workout UI state but must rehydrate/reconcile against committed sessions/sets rather than own a second health-record ledger. Existing TanStack Query rules cover remote/server state: if Query is deliberately used as a read-through view of local repositories, document that extension and invalidation/offline execution semantics first; do not accidentally make local commits depend on network status. These are proposals respecting the existing [import boundaries/state rules](../docs/ARCHITECTURE.md#4-import-boundaries), not edits to those rules.

## Encryption at rest: two different layers

1. **iOS Data Protection** encrypts files using platform keys and a per-file protection class. Apple says third-party app data not otherwise assigned uses Complete Until First User Authentication (Class C); after the first unlock its class key remains available when locked. Complete Protection (Class A) discards the decrypted class key shortly after lock. Therefore “iPhone is encrypted” is not the same guarantee as “PHR inaccessible whenever locked.” [Apple classes](https://support.apple.com/guide/security/data-protection-classes-secb010e978a/web).
2. **SQLCipher** adds database-file encryption and authentication with an app-provided key. Its design specifies AES-256-CBC and per-page HMAC; main database and journal/WAL pages are encrypted, but other temporary files require disabling file-backed temp stores. It does not encrypt Food Draft JPEGs, logical JSON exports, JS logs or in-memory domain objects by itself. [SQLCipher design](https://www.zetetic.net/sqlcipher/design/).
3. **Key lifecycle is part of storage selection.** SecureStore uses iOS Keychain, supports accessibility levels including device-only variants, can outlive uninstall, and warns biometric changes can invalidate authentication-protected items. Proposal: use a random database key stored separately from DB files; explicitly delete it on hard delete; never embed/log it or silently replace a missing key when an existing DB is present. Device-only protection trades new-device restore for stronger binding; mandatory biometric authentication needs a recovery story before protecting irreplaceable data. [SecureStore persistence/options](https://docs.expo.dev/versions/latest/sdk/securestore/).

SQLCipher in Expo requires `useSQLCipher` and a rebuilt native binary, not an OTA-only config change. A `PRAGMA key` on a non-SQLCipher binary can be silently ignored; verify `PRAGMA cipher_version` and fail closed. Enabling the flag does **not** convert an existing plaintext database: plan an explicit encrypted migration. Verify keyed read, wrong/missing-key failure, journal/temp behavior and every connection before calling the app encrypted. [Expo SQLCipher](https://docs.expo.dev/versions/latest/sdk/sqlite/#sqlcipher), [upstream configuration guidance](https://github.com/expo/expo/blob/main/packages/expo-sqlite/skills/expo-sqlite/references/web-and-config.md#sqlcipher).

**Unknown:** actual protection classes of DB, WAL/SHM, MMKV and attachments in the eventual release binary, and the smallest native/config-plugin route to setting/verifying the desired classes and backup exclusions. Reviewed SQLite options do not establish a per-file Class A policy. A foreground-only MVP could prefer Class A; locked-device ingestion might need Class C and separately aligned key accessibility. That is a design trade-off requiring physical-device verification, not a library guarantee. [Apple classes](https://support.apple.com/guide/security/data-protection-classes-secb010e978a/web), [Expo SQLite configuration](https://docs.expo.dev/versions/latest/sdk/sqlite/#configuration-in-app-config).

## Backups and the meaning of “on-device only”

- **Local DB does not mean no cloud copy.** Apple backs Documents and Application Support up by default; Caches/tmp are excluded but purgeable, so they are not a workaround for irreplaceable records. Expo's default iOS database is Documents/SQLite; MMKV's README says Documents/mmkv. For op-sqlite/WatermelonDB inspect the actual resolved path rather than assume the engine decides policy. [Apple locations](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html), [Expo source](https://github.com/expo/expo/blob/sdk-58/packages/expo-sqlite/ios/SQLiteModule.swift), [MMKV path](https://github.com/mrousavy/react-native-mmkv#customize).
- **Proposed strict-local policy:** exclude the PHR directory, attachments, staging snapshots and any persisted health-bearing state from backup using Apple's resource exclusion mechanism; verify behavior for newly created/replaced files and real backup/restore. Keep durable files outside purgeable directories. Losing the phone/uninstalling can then lose the only record unless the user exported it. [Apple exclusion mechanism and directory rules](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html).
- **Alternative for discussion, not an approved equivalent:** backup-enabled local storage improves recovery but violates a literal “data never leaves the device” promise, and needs a compatible key-restore plan. Apple's App Review §5.1.3(ii) states apps may not store personal health information in iCloud; do not assume a SQLCipher blob exempts the app or adopt iCloud backups without resolving policy. Applicability to this app's exact distribution/automatic-backup configuration is **not adjudicated by this research**. [iCloud app-data backups](https://support.apple.com/en-us/108770), [App Review health rules](https://developer.apple.com/app-store/review/guidelines/#health-and-health-research).
- **Encryption is not exclusion.** Encrypted file copies can still leave the phone; `THIS_DEVICE_ONLY` keys cannot be migrated to another device in a backup restore. A backed-up encrypted DB and a nonmigrating key can yield unrecoverable data. Test the pair, not the database alone. [Apple backups](https://support.apple.com/en-us/108770), [SecureStore constants](https://docs.expo.dev/versions/latest/sdk/securestore/#constants).

## Portable export

**Proposed user format:** a versioned JSON manifest/records file (or JSON plus attachment files in an archive), carrying export/schema version, export timestamp, canonical units, timestamps/day keys, provenance, stable IDs and relationships, draft statuses, plan history and chat citations. CSV can be a supplemental tabular convenience, not the sole fidelity-preserving export. Validate the format with Zod and test export/import round trips before treating export as recovery. This format is a project proposal motivated by the [product entity/provenance model](../docs/REQUIREMENT.md#10-data-model--source-of-truth-rules) and [storage-boundary validation rule](../docs/ARCHITECTURE.md#4-import-boundaries).

A raw SQLite snapshot is useful for technical recovery but is not a universal user-readable interchange, particularly when encrypted and key-dependent. Expo exposes online backup and serialization. Use a consistent snapshot/controlled read transaction; **do not copy only the main `.db` while WAL is live**. SQLite's backup API produces a consistent database snapshot; WatermelonDB documents reader blocks for consistent custom export. SQLCipher export/serialization behavior and destination-key handling on the installed Expo binary are **unverified**; do not assume these APIs automatically produce an encrypted or safely shareable file. [Expo backup guidance](https://github.com/expo/expo/blob/main/packages/expo-sqlite/skills/expo-sqlite/references/web-and-config.md#backups-and-serialization), [SQLite backup](https://www.sqlite.org/backup.html), [Watermelon readers](https://watermelondb.dev/docs/Writers#advanced-readers).

Proposal: explicit export consent and plaintext warning, protected temporary staging excluded from backup, cleanup on success/cancel/failure and next-launch cleanup after crashes. User-selected destinations can create off-device copies outside the app's subsequent delete authority; explain that exception to “on-device only.” Apple documents that files handed through system document interactions can leave the app's own container. [Apple file/container model](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html).

## Hard delete: define the boundary honestly

**Single record:** a SQL `DELETE` normally marks space reusable rather than wiping deleted content. SQLite documents `secure_delete` and VACUUM as measures against database-file remnants; `secure_delete` has virtual-table/FTS caveats. Neither is evidence of forensic erasure of all APFS/flash copies or past exports/backups. WatermelonDB's `markAsDeleted` is not permanent destruction; use permanent-delete semantics and explicitly handle descendants if selecting it. [SQLite VACUUM](https://www.sqlite.org/lang_vacuum.html), [secure_delete](https://www.sqlite.org/pragma.html#pragma_secure_delete), [Watermelon deletion](https://watermelondb.dev/docs/Writers#delete-action).

**Proposed delete-all contract:** stop ingestion/queued writes and exporters; drain/finalize work; close all connections; delete the DB and associated sidecars plus attachments, snapshots, export staging and health-bearing KV state; explicitly delete Keychain keys; clear in-memory Query/Zustand/form views; verify absence before showing success; make interrupted cleanup retryable. Expo exposes close/delete APIs, op-sqlite close/delete, MMKV instance deletion and SecureStore key deletion, but app orchestration across these stores is not automatic. [Expo cleanup guidance](https://github.com/expo/expo/blob/main/packages/expo-sqlite/skills/expo-sqlite/references/web-and-config.md#backups-and-serialization), [op-sqlite deletion](https://op-engineering.github.io/op-sqlite/docs/api#delete), [MMKV](https://github.com/mrousavy/react-native-mmkv#delete-an-mmkv-instance), [SecureStore delete](https://docs.expo.dev/versions/latest/sdk/securestore/#securestoredeleteitemasynckey-options).

**Promise only deletion of app-controlled current data.** Key destruction helps only if no usable key copy remains; previously created backups and user exports cannot be recalled by removing current files. iCloud keeps periodic snapshots, and Apple describes user-managed old-backup deletion. Deleting Motive's imported HealthKit copies must not be presented as deleting Apple's independent Health database. Exact forensic erasure and deletion of historical external copies are **not established**. [iCloud snapshot/retention behavior](https://support.apple.com/en-us/108770), [separate app containers](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html).

## Recommendation for the decision

- **Option A — Expo SQLite + explicit SQL migrations + verified iOS Data Protection, without SQLCipher:** least key-management complexity; indexed relational reads and atomic local writes fit the PHR. Trade-off: no independent database-file encryption, and default Class C does not revoke file access on each lock. Select only after accepting the threat model and verifying the intended file classes. [Expo SQLite](https://docs.expo.dev/versions/latest/sdk/sqlite/), [Apple classes](https://support.apple.com/guide/security/data-protection-classes-secb010e978a/web).
- **Option B — Expo SQLite + SQLCipher + Keychain-managed key + explicit migrations:** leading candidate if copied-file protection is required. Trade-off: native rebuild/configuration, key loss/restore policy, plaintext-to-encrypted conversion, attachment protection and keyed transaction-connection testing. SQLCipher is not a replacement for backup exclusion. [Expo SQLCipher](https://docs.expo.dev/versions/latest/sdk/sqlite/#sqlcipher), [connection warning](https://github.com/expo/expo/blob/main/packages/expo-sqlite/skills/expo-sqlite/references/web-and-config.md#sqlcipher), [SecureStore](https://docs.expo.dev/versions/latest/sdk/securestore/).
- **Optional layer on A or B — Drizzle:** choose typed schema/query authoring and generated migrations if they justify extra bundling/build tooling; otherwise direct SQL keeps the stack smaller. It does not change backup/encryption semantics. Verify stable package compatibility rather than copying the current prerelease examples. [Drizzle Expo guide](https://orm.drizzle.team/docs/connect-expo-sqlite).
- **Alternative — op-sqlite (plain or SQLCipher):** consider if a measured workload or required API/extension makes Expo SQLite inadequate; trade native/linking maintenance and app-owned migration/export work for its dedicated-thread execution and richer bindings. No project benchmark currently establishes a need. [API](https://op-engineering.github.io/op-sqlite/docs/api), [Expo linking caveats](https://op-engineering.github.io/op-sqlite/docs/installation#compilation-clashes).
- **Defer WatermelonDB and keep MMKV out of the PHR:** Watermelon adds reactive models but needs proof of stable-SDK/New-Architecture compatibility, encryption approach and safe migration/reset behavior for irreplaceable local data. MMKV is appropriate only for small client preferences if an existing SQLite KV path is insufficient.
