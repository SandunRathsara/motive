## Platform rules no wrapper can change

1. HealthKit authorization is **per type and per direction**. Check `isHealthDataAvailable` first; request only needed read types, with an empty write set initially. Completing the permission request does not mean the user approved every type. A user can change permissions later. [Apple authorization][apple-auth]; [Apple setup][apple-setup].
2. Read denial is deliberately hidden: reads return only the app's own saved samples if external read access was denied. Therefore empty results cannot distinguish denied, genuinely empty, not-yet-synced or out-of-window data; a successful read does not establish continuing access. `authorizationStatus(for:)` is about **sharing/writing**, not reading. [Apple authorization][apple-auth]; [Apple authorizationStatus][apple-status].
3. The current Apple documentation also describes limited-history permission. Kingstinct exposes `getEarliestAuthorizedSampleDates` with an iOS 27+ guard and an empty result on older OS versions. A missing dictionary entry is **not** proof of full access or denial. Do not require this newer API for the iOS 16.4 baseline. [Apple authorization][apple-auth]; [Kingstinct authorization reference][king-auth].
4. An `HKObserverQuery` reports that something changed; query again for actual samples. `HKAnchoredObjectQuery` returns additions **and deletions**, plus an opaque anchor for subsequent deltas. An anchor is not a timestamp or an app-readable memory address, despite AE's documentation wording. [Apple observer query][apple-observer]; [Apple anchored query][apple-anchor]; [AE anchored-workout documentation][ae-anchor].
5. Background delivery needs `com.apple.developer.healthkit.background-delivery` on iOS 15+, observer registration at launch and completion-handler discipline. Delivery frequency is a maximum, not a schedule; steps are capped at hourly. Background queries must be tested on a physical device, not the simulator. These are not guarantees of an always-fresh dashboard. [Apple background delivery][apple-background].

**Implication for the existing requirements (proposed clarification, not a document change):** do not implement `SignalAvailability.authorized/notAuthorized` as detectable read states. Track per type: device/type availability, whether a request was attempted, last successful query, last nonempty sample, empty window, errors, and provenance; keep write authorization separate. Present “No readable samples in this window; check Health access and source sync,” not “permission denied” or zero. This follows Apple's intentional ambiguity. [Apple authorization][apple-auth].

### Configuration details

**All options:** enable `com.apple.developer.healthkit = true`; supply a specific `NSHealthShareUsageDescription` for reading and `NSHealthUpdateUsageDescription` when requesting writes. Do not confuse “Share” in the Info.plist read-purpose key with HealthKit's `toShare` write set. Do not enable clinical records or clinical-purpose descriptions for these seven fitness types. [Apple setup][apple-setup]; [Apple authorization][apple-auth].

- **Kingstinct:** add plugin `@kingstinct/react-native-healthkit`, with explicit read/update purpose strings and explicit `background` choice. The plugin adds background-delivery entitlement **by default** unless `background:false`. `NSHealthUpdateUsageDescription:false` skips adding the write description, useful for a strictly read-only build, but it does not remove an already-existing value. Likewise `background:false` skips adding the entitlement rather than deleting a pre-existing one: inspect generated output after configuration changes. No AppDelegate edits are required by the current implementation. [Main plugin][king-plugin]; [core plugin][king-core-plugin]; [background reference][king-background].
- **AE:** plugin `react-native-health`, options `healthSharePermission`, `healthUpdatePermission`; leave `isClinicalDataEnabled:false`. Its plugin sets the HealthKit entitlement and an empty healthkit.access array, not background-delivery entitlement or launch observers. The background docs use `AppDelegate.m`, an `RCTBridge` and `initializeBackgroundObservers:`, so they are not a turnkey recipe for a modern Expo New Architecture app. Native background setup would need a separately verified reproducible plugin/module rather than hand edits to generated files. [Plugin][ae-plugin]; [Expo guide][ae-expo]; [background guide][ae-background].
- **Custom:** use an app-local Swift Expo module; persist its source outside generated `ios/`. Use app config or a config plugin for HealthKit and optional background entitlements, purpose strings and any native launch integration. Expose a deliberately small, typed API for availability/request/query/delta; validate returned plain DTOs at the service boundary. This is a proposed module design, not existing functionality. [Expo custom native code][expo-custom]; [Expo modules][expo-modules]; [Expo capabilities][expo-capabilities].

### Development-build workflow (all three)

1. After the gate is explicitly decided, install `expo-dev-client` plus the chosen native package(s), configure the plugin and a unique iOS bundle identifier. Kingstinct also needs Nitro; no clinical-record package is needed. [Development-build guide][expo-dev]; [Kingstinct installation][king-readme].
2. Inspect `npx expo config --type introspect` for purpose strings/entitlements. Generate native projects through prebuild, then compile a **new native binary**; an OTA/Metro JS change cannot add HealthKit native code. [Expo capabilities][expo-capabilities]; [development-build guide][expo-dev].
3. Local Mac route: `npx expo run:ios --device`, using Xcode signing and iPhone Developer Mode. EAS route: a development profile, `eas build --platform ios --profile development`, appropriate credentials and registered device. Install the binary and use `npx expo start` for JS iteration. Rebuild when native dependencies/configuration change. No option works in Expo Go. [Development-build guide][expo-dev].
4. EAS synchronizes the base HealthKit capability from entitlements; its published capability list does not separately enumerate the background-delivery sub-entitlement. **Unknown until verified:** provisioning of that sub-option for this account/build. Inspect the signed app and provisioning profile rather than assuming plugin output proves Apple-side authorization. Capability changes can require regenerated profiles. [Expo capabilities][expo-capabilities]; [Apple background delivery][apple-background].

## Apple account and provisioning: personal use versus EAS

**Important correction to a common blanket claim:** Apple's current iOS supported-capabilities table marks **HealthKit yes for all three columns: paid Developer Program, Enterprise Program, and free Apple Developer**. This was checked in the HTML because the Markdown rendering loses the checkmark icons. Thus the primary source does **not** support saying “HealthKit always requires a paid account.” [Apple capability matrix][apple-capabilities].

- **Free local testing:** sign into Xcode with an Apple Account, accept the Developer Agreement, select the Personal Team, use automatic signing and a unique bundle identifier, and enable HealthKit. Xcode manages the account's App IDs, devices, certificates and profiles. Apple's documented limits are 10 App IDs / 3 devices (expire after seven days), at most three apps per device, and seven-day provisioning profiles requiring rebuild/reinstallation. Expo explicitly identifies local compilation as the route to install an iPhone development build without paid membership. **Unknown:** successful signing and background-delivery sub-entitlement support for this exact Personal Team; validate on the owner's account/device before promising it. [Apple account overview][apple-account]; [capability matrix][apple-capabilities]; [Expo development builds][expo-dev].
- **Paid EAS route:** Expo requires paid Apple Developer membership for physical iPhone EAS builds, including EAS local builds; compiling locally through EAS is not the free Xcode route. A paid individual membership is sufficient for an individual workflow; no organization or watchOS target is implied. [Expo development builds][expo-dev]; [Apple account overview][apple-account].
- **Profiles are not user consent:** use a HealthKit-enabled app identifier, corresponding signing certificate and a device-covering development/ad-hoc profile as appropriate. EAS internal distribution uses ad-hoc provisioning and a registered device list; Xcode local development uses its development signing workflow. A valid entitlement/profile only permits calling HealthKit; the on-device per-type permission sheet remains necessary. [Expo internal distribution][expo-internal]; [Apple development profiles][apple-profiles]; [Apple authorization][apple-auth].
- No App Store publication is needed to run your own correctly signed development build. Health data need not leave the phone merely because the binary is built on EAS; keep real health fixtures out of uploaded source, logs and analytics. The former follows the local/EAS installation workflows; the latter is the proposed on-device-only handling policy, not a claim of audited SDK telemetry. [Expo development builds][expo-dev].

## Seven-type coverage and provenance

Read scope below is a **proposed MVP subset**, not permission to request every type in the broader requirements. Kingstinct uses the HealthKit identifiers below with generic quantity/category/workout queries; custom Swift would use the equivalent native types. AE exposes the named methods in its public README/types. [Kingstinct README][king-readme]; [quantity API][king-quantity]; [category API][king-category]; [workout API][king-workouts]; [AE README][ae-readme].

| Signal | Native identifier / proposed normalized representation | Kingstinct | AE |
|---|---|---|---|
| Sleep | `HKCategoryTypeIdentifierSleepAnalysis`; intervals + stage, not a single duration | Category samples, anchors, sourceRevision/device/metadata | `getSleepSamples`; UUID, times, stage, sourceName/sourceId, **no HKDevice or metadata** in its sleep serializer. [AE queries][ae-queries] |
| HRV | `HKQuantityTypeIdentifierHeartRateVariabilitySDNN`; milliseconds, distinguish SDNN from RMSSD | Quantity samples + anchors, explicit unit | `getHeartRateVariabilitySamples`; native method uses **seconds**, so multiply by 1000 for ms; standard quantity provenance. [AE vitals][ae-vitals] |
| Resting HR | `HKQuantityTypeIdentifierRestingHeartRate`; count/min | Quantity samples + anchors | `getRestingHeartRateSamples`; standard quantity provenance. [AE vitals][ae-vitals] |
| Steps | `HKQuantityTypeIdentifierStepCount`; count | Raw quantity and statistics queries; anchors | `getStepCount`, `getDailyStepCountSamples`, generic `getSamples` (`StepCount`); distinguish aggregates from raw samples. [AE README][ae-readme], [AE queries][ae-queries] |
| Active energy | `HKQuantityTypeIdentifierActiveEnergyBurned`; kcal | Quantity samples + statistics + anchors | `getActiveEnergyBurned`; uses standard quantity query. [AE activity][ae-activity] |
| Body mass | `HKQuantityTypeIdentifierBodyMass`; kg | Quantity samples + anchors | `getWeightSamples`; default is **pounds**, so explicitly normalize to kg. [AE body][ae-body] |
| Workouts | `HKWorkoutTypeIdentifier`; activity, interval, duration, summary statistics, provenance | Workout proxies, anchored additions/deletions; convert `toJSON()` before caching | `getSamples` / `getAnchoredWorkouts`; sourceName/sourceId, metadata, simplified device string; anchored API discards deletions. [AE queries][ae-queries], [Kingstinct README][king-readme] |

**Kingstinct provenance:** quantity/category serialization includes UUID, start/end, metadata, `sourceRevision` (source name/bundle identifier, version, OS, productType) and optional `device` (name, manufacturer, model, hardware/software/firmware, local/UDI identifiers). Workout proxies also expose sample data and plain serialization. Missing device fields remain missing; they cannot be made authoritative by the wrapper. Some unsupported metadata value types are dropped with a warning, per changelog. [Serializers][king-serializers]; [workout proxy][king-workout-proxy]; [changelog][king-changelog].

**AE provenance:** the shared quantity serializer returns UUID, value, times, sourceName/sourceId and optional metadata, **not full source revision or HKDevice**. This covers weight, HRV, RHR and active energy; sleep's serializer omits even metadata. Generic `getSamples` has simplified device/source data for supported types; daily statistics produce aggregation-specific output, not sample-level provenance. AE's `device` is usually `sourceRevision.productType`, not an `HKDevice` object. Do not label these fields interchangeable with Kingstinct's full device DTO. [Queries implementation][ae-queries]; [body methods][ae-body]; [vitals methods][ae-vitals]; [activity methods][ae-activity].

**Proposed local adapter contract:** retain sample UUID/type/start/end/value+explicit-unit or stage, source bundle ID/name, source revision, optional device, and a small allowlisted metadata subset (including user-entered indication when supplied). Validate DTOs, distinguish raw samples from aggregated statistics, and never fabricate a device from a display name. Device-only readiness filtering requires a documented provenance policy; source metadata is evidence, not proof of sensor accuracy. This proposal preserves the available fields above and acknowledges optionality. [Kingstinct serializers][king-serializers]; [AE queries][ae-queries].

## Sync and acceptance checks before adoption

Proposed acceptance checklist, not a report of completed tests:

- Bootstrap the actual stable Expo version, lock dependencies, run existing typecheck/lint/test/architecture gates and Expo Doctor, then build SDK 58 / RN 0.88 on the owner's iPhone. A peer-range match is not enough. [Expo dependency validation][expo-new]; [Kingstinct example baseline][king-example].
- Inspect generated and signed entitlements, purpose strings and provisioning; exercise free Personal Team versus paid EAS only for the chosen deployment route. Specifically verify optional background delivery instead of inferring it from base HealthKit support. [Apple capability matrix][apple-capabilities]; [Expo capabilities][expo-capabilities].
- Request all seven reads with **no writes**; test partial approval, all-denied, empty windows, revocation and unavailable data. UI must not infer denied/zero from an empty result. [Apple authorization][apple-auth].
- Import staged sleep, SDNN HRV, RHR, steps, energy, weight and a completed workout; verify units, dates, timezone boundaries, manual-source handling and optional provenance. Do not sum overlapping sleep stages/in-bed intervals or blindly sum duplicate multi-source activity samples. These are proposed correctness checks motivated by raw source/stage data, not a claim that either wrapper reconciles sources automatically. [Kingstinct serializers][king-serializers]; [AE sleep docs][ae-sleep]; [AE queries][ae-queries].
- If maintaining a local sample cache, apply UUID additions and deletions before advancing a per-type/query anchor; exercise pagination, invalid-anchor recovery, late-arriving samples and deletion-only batches. Persistence/retention/backup decisions remain separate gates; do not add storage as a side effect of choosing a wrapper. Anchors only have meaning with the cache/query they track. [Apple anchored query][apple-anchor]; [Kingstinct changelog][king-changelog].
- Start with foreground refresh/on-resume plus honest `lastSyncedAt`; evaluate background delivery separately. Test cold start, locked phone, no JS listener yet and later foreground catch-up on device. Maintainer claims about native buffering are useful evidence, not a replacement for these tests. [Apple background delivery][apple-background]; [Kingstinct background reference][king-background].

## Recommendation for the decision

These are ranked options for the coordinator/owner, **not a final decision or authorization to implement**:

1. **Evaluate Kingstinct 16.2.0 first**, behind the health feature service boundary, with Nitro, explicit plugin settings, seven read types and foreground refresh initially. It offers the best evidenced fit here: typed generic coverage, full available provenance and deletion-aware anchors. Trade-offs: a Nitro/native dependency, recent breaking changes and **unverified SDK 58/RN 0.88 real-device compatibility**; its older Expo example is not enough evidence to close that gate. [Manifest][npm-king-version]; [example][king-example]; [changelog][king-changelog]; [serializers][king-serializers].
2. **Use a narrow custom Expo module if that build/provenance spike fails** or native background lifecycle control becomes a demonstrated need. Trade-off: fewer wrapper dependencies and an exact app-sized contract, but the project owns HealthKit query serialization, anchors/deletions, signing configuration and lifecycle testing. Expo's New Architecture support removes one framework uncertainty, not these implementation obligations. [Expo modules][expo-modules]; [Apple anchored queries][apple-anchor]; [Apple background delivery][apple-background].
3. **Keep AE react-native-health as a lower-priority alternative**, not the default greenfield choice: the simple Expo plugin and broad existing getters help, but source/device fidelity, dropped anchored-workout deletions, background-plugin gaps and old published baseline raise the amount of patching and verification for this app. Do not claim it is categorically incompatible without a build test. [Registry][npm-ae]; [queries][ae-queries]; [Expo guide][ae-expo]; [README][ae-readme].

For deployment, choose **free local Xcode Personal Team testing** if weekly reinstall friction is acceptable, versus **paid individual membership + EAS** for the supported EAS real-device path.
