# AI Coach model provider and stateless proxy hosting

Research resolution for [issue #4](https://github.com/SandunRathsara/motive/issues/4), supporting [Phase 1 roadmap #1](https://github.com/SandunRathsara/motive/issues/1). **Checked: 1 November 2026. Status: options and decision inputs, not an accepted architecture decision.** Prices are USD before tax; live vendor pages can change.

## Scope and answer in brief

The supplied ticket context is authoritative for this investigation: one personal iPhone, no accounts, on-device Personal Health Record (PHR), one proxy holding model credentials, and an AI Coach that **explains deterministic Plan Changes and answers grounded questions but cannot change the plan**. The checked-in [TECH_STACK §4–6](../docs/TECH_STACK.md#4-backend-and-secrets) leaves provider, authentication, and health transmission gates open. [REQUIREMENT §12](../docs/REQUIREMENT.md#12-ai-safety--privacy-requirements) requires consent, evidence, wellness-only behavior, and fixed escalation cards. Its older prototype/LLM-proposal language is not permission to broaden the ticket's explanation-only model role.

**Research assessment:** shortlist a direct OpenAI API or Anthropic API behind a small Cloudflare Worker; Vercel Functions is a plausible personal-use alternative. Do not equate no-training terms with zero retention. Do not call App Attest fully stateless: Apple's protocol explicitly stores challenges, verified keys, and counters. Supabase's documented invocation logging is a blocker until body/header capture can be ruled out or disabled. These are recommendations to evaluate, not selections. Evidence follows.

### ZDR is scoped, not literal absence of all data

- OpenAI documents retained billing/system metadata and feature-specific application state; current prompt-caching notes allow encrypted KV tensors in GPU-local storage up to 24 hours. A small cache TTL is not a maximum-retention switch. Avoid background mode, hosted retrieval, uploads, search, MCP and containers for this proxy; recheck the chosen model's cache and ZDR behavior before sending real data. [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data)
- Anthropic structured-output schemas may be cached up to 24 hours since last use even under qualified ZDR. Keep **all health facts, dynamic evidence IDs, names and user-specific enum values out of schema definitions**; put them in message content and validate IDs against the request locally. Its ZDR retains legal/flagged-content exceptions. [API retention](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention), [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- Provider deletion/export guarantees cannot be inferred from deleting the on-device chat. Do not promise immediate deletion from abuse-monitoring archives; explain the selected vendor's scope in consent. This follows the retention policies above and the [product deletion/consent requirements](../docs/REQUIREMENT.md#12-ai-safety--privacy-requirements).

## 5. Authentication without accounts—and the statelessness conflict

### App Attest: app integrity, not owner authorization

Apple's App Attest creates a hardware-based key, attests the legitimate app instance, and signs requests. Server validation checks Apple certificates, challenge binding, App ID, environment and the assertion signature. The server must remember a unique one-time challenge, store the verified public key/receipt, compare the assertion counter with the prior counter, and store the new counter. **Inference: replay-safe App Attest requires security state; it cannot honestly be described as strictly storage-free.** [Apple server validation](https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server) ([machine-readable article used for inspection](https://developer.apple.com/tutorials/data/documentation/devicecheck/validating-apps-that-connect-to-your-server.json))

The private key stays in the Secure Enclave, but App Attest keys do not survive reinstall, device migration or backup restoration; availability must be checked with `isSupported`. Plan enrollment recovery and a safe unsupported-device policy. Apple's example bypasses attestation when unavailable; for this single-owner paid proxy, a proposed safer fallback is explicitly enrolled owner credentials or cloud-coach unavailable—not anonymous model access. [Apple client integration](https://developer.apple.com/documentation/devicecheck/establishing-your-app-s-integrity)

Attesting **any** genuine installation of this app does not prove it is the one owner's authorized phone. Proposed authorization: owner manually approves the attested key fingerprint using a trusted admin channel; no user account needed. Do not make enrollment open solely because attestation passed. This is a threat-model conclusion based on Apple's [app-instance integrity scope](https://developer.apple.com/documentation/devicecheck/establishing-your-app-s-integrity), not an additional Apple identity guarantee.

| Scheme | Proposed enrollment / request check | Trade-off and state |
|---|---|---|
| **App Attest + owner allowlist** | One-time owner approval; per-call assertion binds challenge + HTTP method/path + exact body digest; verify identity/environment and atomically consume challenge/update counter before forwarding. | Highest app-integrity assurance of these options, but native integration and security state required. Store only key/receipt, counter, expiring challenges, revocation and quota metadata—**never health/chat bodies**. Apple describes key/challenge/counter persistence; request binding and atomicity are proposed application controls. [Apple validation](https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server) |
| **Owner-enrolled device key / device-bound token** | Generate non-exportable Secure Enclave P-256 key; owner pins its public key in server configuration. Sign method/path/body hash plus timestamp and nonce. If issuing short-lived tokens, bind them to proof of possession rather than accepting an exportable bearer alone. | Simpler for one phone; proves possession of the enrolled key, **not** that app code is genuine. Public-key pin can be static config, but strict one-time replay prevention needs a nonce/counter store. Timestamp-only validation leaves a replay window. Secure Enclave key properties: [Apple key protection](https://developer.apple.com/documentation/security/protecting-keys-with-the-secure-enclave). Enrollment/token/replay design is a proposal, not a built-in Apple proxy feature. |
| **Manually provisioned per-install bearer secret** | Owner transfers a random credential out-of-band to device secure storage; proxy keeps verifier/config and rotates on loss. No model key in app. | Least implementation work, no app-integrity proof, credential theft permits replay until revoked. Accept only as an explicit single-user risk trade-off; Keychain protection does not make a bearer credential non-exportable or device-bound. [Apple key protection](https://developer.apple.com/documentation/security/protecting-keys-with-the-secure-enclave) explains distinction from non-exportable keys. |
| **One shared secret embedded in app binary** | Every copy carries the same credential. | Do not use as the production protection boundary: public-client software cannot keep a shared static secret confidential. [OAuth native-app security standard §8.5](https://www.rfc-editor.org/rfc/rfc8252#section-8.5) |

A server-signed expiring challenge/token carried entirely by the client can establish integrity and expiry, but without consumption state the same valid challenge/request can be replayed within its validity window. Storing the last counter only inside such a token does not prevent rolling back to an older token. This is a protocol-design inference from Apple's [one-time challenge and monotonic-counter checks](https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server).

**Decision needed:** interpret “stateless proxy” as **health/content-stateless**, permitting tiny durable security/quota state, or require literal request-statelessness and explicitly accept weaker replay/revocation/spend controls. No accounts and no server-side PHR do not logically prohibit a security record. For strict concurrency-safe quotas/counters, a storage primitive must be chosen under the [stack decision gates](../docs/TECH_STACK.md#6-decision-records); this research does not silently add a database or extra service.

**Proposed abuse controls:** owner-only enrollment, bounded request/context/output sizes, fixed model allowlist, short timeouts, bounded retries, rate/concurrency limits, atomic usage quota and upstream key kill switch. Reject unauthorized requests before reading/forwarding sensitive content where practical. A truly stateless proxy cannot enforce a reliable cumulative monthly quota across invocations; model/host budget alerts alone should not be called hard caps. These are threat-model recommendations; actual provider spend-cap behavior remains **unverified**.

## 6. Privacy release gates and unknowns

1. **Consent before transmission:** disclose selected proxy/model provider, exactly which derived health facts and chat are sent, purposes, retention, exceptions, and how to disable cloud coaching. Apple's guideline 5.1.2(i) explicitly requires permission for sharing personal data with third-party AI; §5.1.3 adds health-data constraints. HealthKit read authorization is not a substitute for this AI disclosure. [App Review guidelines](https://developer.apple.com/app-store/review/guidelines/#data-use-and-sharing), [Health rules](https://developer.apple.com/app-store/review/guidelines/#health-and-health-research)
2. **Retention policy choice:** either accept disclosed standard no-training API retention or require confirmed contractual ZDR for the exact organization/model/features. If strict ZDR is mandatory and not available, keep cloud coaching off; deterministic local explanations still work. Approval, minimum spend and processing geography are **unknown**. Sources: [OpenAI](https://developers.openai.com/api/docs/guides/your-data), [Anthropic](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention), [Gemini](https://ai.google.dev/gemini-api/docs/usage-policies).
3. **Safety stays deterministic:** local plan engine alone owns Plan Changes; fixed escalation UX and data-exclusion rules must survive model failure. Do not depend only on vendor safety filters or allow streamed unvalidated prose to bypass guardrails. Proposed enforcement derives from [product §12](../docs/REQUIREMENT.md#12-ai-safety--privacy-requirements).
4. **Outstanding verification:** task-quality bake-off; actual account/model availability; Anthropic retention wording conflict; Gemini personal-use eligibility; runtime compatibility/CPU of attestation; full-host logging disablement and infrastructure retention; on-device credential lifecycle; replay-safe security-state exception. None was experimentally verified here.
5. **HIPAA/legal status:** no claim that a vendor BAA or ZDR makes this app compliant or that personal use automatically exempts it from all privacy obligations. This is wellness research, not legal advice. Vendor HIPAA arrangements are separate account/feature commitments: [OpenAI controls](https://developers.openai.com/api/docs/guides/your-data), [Claude HIPAA readiness](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention#hipaa-readiness).

Context7 resolved the official OpenAI documentation collection and retrieved current retention guidance; critical claims were checked against direct vendor pages.
